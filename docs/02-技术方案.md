# PiDesk 技术方案

## 1. 技术选型

### 1.1 决策矩阵

桌面外壳有三条主流路线，核心差异在于「能否直接复用 Pi 的 `RpcClient` 与 TS 类型」。

| 维度 | Electron（React+TS） | Tauri 2.0（Rust+WebView） | Wails（Go+WebView） |
|---|---|---|---|
| 复用 `RpcClient` | ✅ 主进程 Node 直接 `import` | ❌ 需在 Rust 侧重写 JSONL 协议客户端 | ❌ 需在 Go 侧重写 |
| 复用 `@earendil-works` TS 类型 | ✅ 全量复用（事件/消息/工具类型） | ❌ 需手写 Rust 类型镜像 | ❌ 需手写 Go 类型镜像 |
| 打包体积 | ~90–130 MB | ~8–15 MB | ~10–20 MB |
| 内存占用 | 较高（含 Node+Chromium） | 低（系统 WebView2） | 低 |
| 开发速度 | **最快**（技术栈单一、类型直通） | 中（前端同，后端 Rust 有学习/桥接成本） | 中 |
| 生态/示例（AI 聊天类桌面） | 最丰富 | 丰富 | 一般 |
| 与 Codex/Hermes「轻量」气质契合 | 一般 | **最佳** | 较好 |

### 1.2 推荐结论

- **首选：Electron + React + TypeScript + Vite**。
  - 决定性理由：Pi 已导出成熟的、typed 的 `RpcClient`，Electron 主进程是 Node 环境，可**零成本直接复用**，协议、事件、工具、消息类型全部直通前端，开发风险和维护成本最低。
  - 代价：exe 体积大（可接受，个人开发工具场景不敏感）。
- **备选：Tauri 2.0**（当你更看重 <15MB 的精简 exe、原生气质、低内存时）。
  - 需要在 Rust 侧实现一个 JSONL 协议客户端（spawn `pi --mode rpc`，按 `\n` 分帧，`serde_json` 解析，经 Tauri Event 转发给前端；前端命令经 Tauri `command` 序列化写回 stdin）。工作量中等但明确，前端代码可与 Electron 版共用 90%。

> 本方案后续以 **Electron 首选路线** 展开；Tauri 差异点在需要处以「备选」标注。

### 1.3 技术栈清单（Electron 首选）

- **运行时/框架**：Electron 32+、Node 22（与本地 managed 版本一致）
- **前端**：React 18 + TypeScript 5 + Vite（`electron-vite` 脚手架）
- **状态管理**：Zustand（轻量，契合事件流驱动的状态机）
- **UI 组件/样式**：Tailwind CSS + Radix UI（无障碍原语） + lucide 图标
- **Markdown/代码高亮**：`react-markdown` + `shiki`（VS Code 同款高亮，与 Pi 的语法高亮观感一致）
- **Diff 渲染**：`diff`（Pi 依赖同款）+ 自绘或 `react-diff-view`
- **依赖复用**：`@earendil-works/pi-coding-agent`（取 `RpcClient` 与全部类型）
- **打包**：`electron-builder`（产出 NSIS 安装包 + portable 单 exe）

## 2. 系统架构

```
┌──────────────────────────────────────────────────────────────┐
│                        PiDesk (Electron App)                    │
│                                                                  │
│  ┌────────────────────────┐        ┌────────────────────────┐  │
│  │   Renderer (React)      │  IPC   │   Main Process (Node)   │  │
│  │                         │◄──────►│                         │  │
│  │  • 对话流视图            │ events │  • PiKernel 封装         │  │
│  │  • 工具卡片 / diff       │commands│    └ RpcClient 实例       │  │
│  │  • 输入区 / 命令面板      │        │  • 会话/窗口管理          │  │
│  │  • 审批弹窗              │        │  • 配置读写(~/.pi)        │  │
│  │  • 会话侧栏 / 会话树      │        │  • 审批扩展生命周期        │  │
│  └────────────────────────┘        └───────────┬────────────┘  │
│                                                  │ spawn         │
└──────────────────────────────────────────────────┼─────────────┘
                                                    │ stdin/stdout (JSONL)
                                     ┌──────────────▼──────────────┐
                                     │   pi --mode rpc              │
                                     │   (@earendil-works/pi-...)   │
                                     │   -e <内置审批扩展>           │
                                     └──────────────┬──────────────┘
                                                    │
                                     ┌──────────────▼──────────────┐
                                     │  LLM Provider (deepseek 等)  │
                                     │  本地工具: read/bash/edit/... │
                                     └─────────────────────────────┘
```

分层职责：

1. **Main Process（Node）**：应用生命周期、窗口、`PiKernel`（对 `RpcClient` 的二次封装，管理多会话/多进程）、配置读写、审批扩展注入。**唯一持有 `RpcClient` 的地方**。
2. **Renderer（React）**：纯 UI + 本地状态机；通过 Electron `contextBridge` 暴露的安全 API 与 Main 通信，不直接触碰子进程。
3. **Pi RPC 子进程**：Pi 内核本体，`PiKernel` 通过 `RpcClient` 启动与驱动。

> 安全：Renderer 开启 `contextIsolation: true`、`nodeIntegration: false`，仅通过 `preload` 的 `contextBridge` 暴露白名单 IPC 方法。

## 3. 通信层设计

### 3.1 Main ↔ Renderer 的 IPC 契约

采用「命令用 `invoke`（请求-响应），事件用 `send`（单向广播）」的模式，镜像 Pi RPC 的 command/event 二分。

**Renderer → Main（`ipcRenderer.invoke`，一一对应 RpcClient 方法）**

```ts
// preload 暴露的 window.pi API（白名单）
interface PiBridge {
  // 会话生命周期
  startSession(opts: { cwd: string; provider?: string; model?: string }): Promise<string /*sessionId*/>;
  stopSession(sessionId: string): Promise<void>;
  // 对话
  prompt(sessionId: string, message: string, images?: ImageRef[]): Promise<void>;
  steer(sessionId: string, message: string): Promise<void>;
  followUp(sessionId: string, message: string): Promise<void>;
  abort(sessionId: string): Promise<void>;
  // 模型 / 思考等级
  getAvailableModels(sessionId: string): Promise<ModelInfo[]>;
  setModel(sessionId: string, provider: string, modelId: string): Promise<void>;
  setThinkingLevel(sessionId: string, level: ThinkingLevel): Promise<void>;
  // 会话历史 / 树 / 分支
  getEntries(sessionId: string, since?: string): Promise<{ entries: SessionEntry[]; leafId: string | null }>;
  getTree(sessionId: string): Promise<{ tree: SessionTreeNode[]; leafId: string | null }>;
  fork(sessionId: string, entryId: string): Promise<void>;
  switchSession(sessionId: string, path: string): Promise<void>;
  // 其它
  bash(sessionId: string, command: string): Promise<BashResult>;
  compact(sessionId: string): Promise<void>;
  exportHtml(sessionId: string, out?: string): Promise<{ path: string }>;
  // 审批响应（回应 approval-request 事件）
  respondApproval(requestId: string, decision: { confirmed: boolean } | { cancelled: true }): Promise<void>;
}
```

**Main → Renderer（`webContents.send`，转发 Pi 事件 + 审批请求）**

```ts
// 频道: "pi:event"
type PiOutboundEvent =
  | { sessionId: string; kind: "agent-event"; event: AgentSessionEvent }   // 原样转发 Pi 事件
  | { sessionId: string; kind: "approval-request"; requestId: string;      // 来自 extension_ui_request
      toolName: string; input: unknown; title: string; message: string }
  | { sessionId: string; kind: "state"; state: RpcSessionState }
  | { sessionId: string; kind: "process-exit"; code: number; stderr: string };
```

> **备选（Tauri）**：把上表的 `invoke` 映射为 Tauri `#[command]`，`send` 映射为 `app.emit`；Rust 侧维护 `Child` 进程与 JSONL reader。前端 API 面保持不变。

### 3.2 `PiKernel`（Main 进程核心封装）

```ts
class PiKernel {
  private sessions = new Map<string, RpcClient>();

  async start(opts): Promise<string> {
    const client = new RpcClient({
      cwd: opts.cwd,
      provider: opts.provider,
      model: opts.model,
      // 注入内置审批扩展，开启图形化确认
      args: ["-e", APPROVAL_EXTENSION_PATH],
    });
    await client.start();
    const id = uuid();
    // 1) 转发所有 agent 事件
    client.onEvent((event) => this.emit(id, { kind: "agent-event", event }));
    // 2) 监听 extension_ui_request（审批/对话框）——见 §5
    this.sessions.set(id, client);
    return id;
  }
  // prompt/steer/abort/... 逐一代理到对应 RpcClient 方法
}
```

### 3.3 流式渲染策略（Renderer）

- 维护 `messages: Map<messageId, MessageVM>` 与 `toolCalls: Map<toolCallId, ToolCallVM>` 两个状态表。
- `message_update` → 累积增量文本，节流（rAF / 每 16–33ms）触发一次重渲染，避免逐 token 抖动。
- `tool_execution_start/update/end` → 创建/更新/定稿对应工具卡片。
- `agent_settled` → 解除「运行中」状态，恢复输入区可编辑、隐藏中止按钮。
- 断线/进程退出（`process-exit`）→ 顶部横幅提示，提供「重连」按钮（重新 `startSession` 并 `switchSession` 到原 session 文件）。

## 4. 数据 / 状态模型（Renderer）

```ts
interface AppState {
  activeSessionId: string | null;
  sessions: Record<string, SessionVM>;
}
interface SessionVM {
  id: string;
  name?: string;
  cwd: string;
  model?: { provider: string; id: string };
  thinkingLevel: ThinkingLevel;
  status: "idle" | "streaming" | "compacting" | "retrying";
  timeline: TimelineItem[];              // 有序的消息 + 工具卡 + 系统事件
  queue: { steering: string[]; followUp: string[] };
  stats?: { messageCount: number; tokens?: number };
  pendingApproval?: ApprovalRequestVM;   // 当前待处理的审批

type TimelineItem =
  | { type: "user"; text: string; images?: ImageRef[] }
  | { type: "assistant"; id: string; text: string; streaming: boolean }
  | { type: "tool"; toolCallId: string; toolName: string; input: unknown;
      result?: unknown; isError?: boolean; state: "running" | "done" }
  | { type: "system"; kind: "compaction" | "retry" | "model-change" | "info"; text: string };
```

## 5. 工具审批扩展（图形化确认）

由于 Pi 协议无原生审批，PiDesk **随包附带一个 Pi 扩展**，随 RPC 进程一起加载（`-e`）。

扩展逻辑（示意，运行在 Pi 进程内）：

```ts
// approval-extension.ts —— 打包进 PiDesk 资源目录
export default function (pi) {
  pi.on("tool_call", async (event, ctx) => {
    const risky = ["bash", "edit", "write"];        // 可配置：哪些工具需要确认
    if (!risky.includes(event.toolName)) return;    // 只读工具直接放行
    const ok = await ctx.ui.confirm(
      `允许执行 ${event.toolName}?`,
      formatToolInput(event.toolName, event.input)  // bash 显示命令、edit 显示 diff 摘要
    );
    if (!ok) return { block: true, reason: "用户在 PiDesk 中拒绝" };
    // 返回 undefined = 放行
  });
}
```

- `ctx.ui.confirm` 在 RPC 模式下 → 发 `extension_ui_request`（`method:"confirm"`）。
- `PiKernel` 拦截该消息 → 转成 `approval-request` 事件推给 Renderer → 弹出审批弹窗。
- 用户点击「允许/拒绝」→ Renderer 调 `respondApproval(requestId, ...)` → Main 把 `extension_ui_response` 写回 Pi stdin。
- **审批开关**：设置项「自动执行 / 危险工具需确认 / 全部需确认」映射为扩展的 `risky` 列表（可通过环境变量或配置文件传给扩展）。

> 该设计同时天然支持 Pi 扩展的其它 UI 请求（`select` / `input` / `notify` / `setStatus` / `setWidget`），PiDesk 可据此渲染下拉选择、通知条、底部状态、待办挂件等。

## 6. 配置与多环境

- **模型/Provider**：读写 `~/.pi/settings.json` 与 `~/.pi/agent/models-store.json`；UI 的模型切换直接调 `setModel`，并可选择持久化到 settings。
- **API Key / Auth**：沿用 Pi 的 `~/.pi/agent/auth.json` 与各 `XXX_API_KEY` 环境变量，PiDesk 不另存密钥（安全上不接管凭据）。
- **工作目录（cwd）**：每个会话绑定一个项目目录（对标 Codex/Hermes 的「在某个仓库里开一个会话」）；侧栏可切换最近项目。
- **PiDesk 自身配置**：`~/.pidesk/config.json`（主题、快捷键、审批策略、字体、最近项目列表）。

## 7. 打包为 .exe

- 工具：`electron-builder`。
- 产物：
  - **NSIS 安装包**（`PiDesk-Setup-x.y.z.exe`，带开始菜单/桌面快捷方式、自动更新预留）。
  - **Portable 单文件**（`PiDesk-x.y.z-portable.exe`，免安装）。
- **Pi 依赖处理**（两种策略）：
  1. **依赖本机已装 pi**（推荐默认）：运行时定位 `pi.cmd` / `dist/cli.js`（查 npm global、PATH、`~/.pi`），`RpcClient` 的 `cliPath` 指向它。体积小，Pi 升级自动生效。
  2. **内置 Pi**（可选）：将 `@earendil-works/pi-coding-agent` 作为 app 依赖一并打包，保证开箱即用但体积更大、需自行跟随 Pi 版本。
- **代码签名**：个人使用可跳过；如需去除 SmartScreen 警告再考虑签名证书。

## 8. 备选路线（Tauri）差异清单

若最终选 Tauri，仅以下模块需替换，前端 React 代码基本复用：

1. `src-tauri/` Rust 后端：`std::process::Command` spawn `pi --mode rpc`；`tokio` 异步按 `\n` 读 stdout；`serde_json` 解析后 `app.emit("pi:event", ...)`。
2. 命令写入：Tauri `#[command]` 收前端请求 → 序列化 JSONL → 写子进程 stdin。
3. 类型：Rust 侧只需为「命令入参」定义 struct，事件可 `serde_json::Value` 透传给前端由 TS 类型约束。
4. 打包：`tauri build` 产出 MSI/NSIS，体积 <15MB，依赖 WebView2（Win10/11 通常已内置）。
