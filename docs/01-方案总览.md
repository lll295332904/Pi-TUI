# PiDesk 方案总览

## 1. 项目目标

为本地已安装的 **PI Agent**（`@earendil-works/pi-coding-agent`）制作一个 Windows 桌面应用（可打包为 `.exe`），**取代其原生命令行 TUI**，提供更符合个人使用习惯的图形界面。

核心诉求：

1. **保留 Pi 全部能力**：会话、流式回复、模型/思考等级切换、工具执行（read/bash/edit/write 等）、会话历史与分支、上下文压缩。
2. **交互模式对标 Hermes TUI / Codex**：键盘优先、单一主对话流、底部输入区、命令面板、会话侧栏。
3. **图形界面增强**：可折叠的工具调用卡片、代码 diff 高亮渲染、bash 输出面板、会话树可视化、模型/token 状态栏、图形化审批弹窗。
4. **独立可分发**：产出单文件或安装包形式的 `.exe`，可在个人 Windows 环境直接运行。

## 2. 关键调研结论（决定方案可行性）

以下结论来自对本地安装包 `C:\Users\nalch\AppData\Roaming\npm\node_modules\@earendil-works\pi-coding-agent\dist`（v0.82.0）源码与类型定义的直接分析。

### 2.1 Pi 提供三种运行模式

`pi` 启动入口 `dist/cli.js` → `main(argv)`，通过 `--mode` 分派：

| 模式 | 启动方式 | 用途 |
|---|---|---|
| `interactive`（默认） | `pi` | 原生终端 TUI（我们要取代的对象） |
| `print` / `json` | `pi -p` / `pi --mode json` | 非交互，一次性输出（text 或 JSONL 事件流） |
| **`rpc`** | `pi --mode rpc`（或 `dist/rpc-entry.js`） | **程序化接口——桌面 UI 的驱动通道** |

> **核心判断**：Pi 官方就为「被外部程序驱动」设计了 RPC 模式。桌面 UI 属于官方支持的集成路径，而非 hack。

### 2.2 RPC 协议（stdin/stdout + JSONL）

- **传输**：子进程 stdin 写命令、stdout 读响应/事件，均为 **换行分隔的 JSON（JSONL）**。分帧**只按 `\n`**（协议注释明确要求：payload 内可能含 U+2028/U+2029，不能用 Node `readline`）。
- **stdout 纯净**：RPC 模式接管 stdout，只输出协议消息；所有日志/诊断走 **stderr**。
- **三类消息**（按 `type` 字段分派）：
  - **Command**（客户端→服务端）：如 `{ "type":"prompt", "id":"1", "message":"..." }`，可带 `id`。
  - **Response**（服务端→客户端）：`{ "type":"response", "id":"1", "command":"prompt", "success":true, "data":... }`，回显同一 `id`。
  - **Event**（服务端广播，无 id）：`AgentSessionEvent` 事件流，驱动 UI 状态。
- **额外通道**：`extension_ui_request` / `extension_ui_response`（扩展 UI，用于审批/对话框，见 §2.5）。

### 2.3 已封装好的 `RpcClient`（决定选型的关键）

包内导出了一个**完整 TypeScript typed 的客户端类** `RpcClient`（`dist/modes/rpc/rpc-client.js`），它自动 spawn `pi --mode rpc` 子进程并封装了全部协议方法：

```ts
import { RpcClient } from "@earendil-works/pi-coding-agent";

const client = new RpcClient({ cwd, provider, model });
await client.start();
const off = client.onEvent((e) => renderEvent(e));   // 订阅事件流
await client.prompt("帮我重构这个文件");               // 发送用户消息
await client.waitForIdle();                            // 等待本轮完成
```

`RpcClient` 已提供的方法（节选）：`prompt / steer / followUp / abort / newSession / getState / setModel / cycleModel / getAvailableModels / setThinkingLevel / compact / bash / abortBash / getEntries / getTree / fork / clone / switchSession / setSessionName / getMessages / getCommands / exportHtml / onEvent / waitForIdle / collectEvents / promptAndWait`。

> **结论**：只要桌面 UI 用 Node/TS 运行主进程，就能 **直接 `import { RpcClient }`**，无需重新实现协议。这是推荐 Electron 的决定性理由（详见 `02-技术方案.md`）。

### 2.4 事件流（UI 渲染的数据源）

服务端把每个 `AgentSessionEvent` 直接推到 stdout。桌面 UI 关注的核心事件：

| 事件 `type` | 用途 |
|---|---|
| `agent_start` / `turn_start` | 开始运行 / 新一轮 |
| `message_start` | 新的 assistant 消息开始 |
| `message_update`（含 `assistantMessageEvent`） | **流式增量 token**，用于逐字渲染 |
| `message_end` | 消息定稿 |
| `tool_execution_start`（`toolName`+`args`） | **工具调用开始** → 渲染工具卡片 |
| `tool_execution_update`（`partialResult`） | 工具执行中间输出（如 bash 流式） |
| `tool_execution_end`（`result`+`isError`） | 工具结果 → 更新卡片 |
| `turn_end` | 一轮结束 |
| `agent_settled` | **完全空闲**（`waitForIdle` 的依据） |
| `queue_update` | steering / follow-up 队列变化 |
| `compaction_start` / `compaction_end` | 上下文压缩 |
| `auto_retry_start` / `auto_retry_end` | 自动重试 |
| `entry_appended` | 会话新增条目（可用于增量刷新） |
| `thinking_level_changed` / `session_info_changed` | 状态变更 |

### 2.5 工具审批机制（重要设计约束）

- **默认行为**：RPC / 交互模式下，内置工具（含 `bash`/`edit`/`write`）**自动执行，无原生「执行前确认」**。协议里**没有** `tool_approval_requested` / `approve` / `deny`。
- **要实现图形化审批，唯一正确途径是加载一个 Pi 扩展**：扩展在 `tool_call` 钩子里调用 `ctx.ui.confirm(...)`；RPC 模式下这会转成 `extension_ui_request`（`method:"confirm"`）发给桌面 UI，UI 弹确认框后回 `extension_ui_response`。
- 我们的方案将**随桌面 UI 附带一个内置审批扩展**（`pi --mode rpc -e <审批扩展路径>`），把「危险工具执行前确认」变成可开关的图形化能力。详见 `02-技术方案.md` §5。

### 2.6 会话存储格式

- 位置：`~/.pi/agent/sessions/<encoded-cwd>/*.jsonl`（可用 `--session-dir` / `PI_SESSION_DIR` 覆盖）。
- 结构：append-only JSONL，首行 `SessionHeader`，后续为 `SessionEntry`（message / model_change / compaction / session_info / label 等），以 `id`/`parentId` 组成**树**（支持分支/fork）。
- UI 可用 `getEntries({since})` 增量拉取、`getTree()` 渲染会话树。

## 3. 整体结论

- **可行性**：高。Pi 原生 RPC + 官方 `RpcClient` 使桌面 UI 成为「纯前端外壳」，不触碰 Pi 内核源码，Pi 升级时兼容成本低。
- **推荐路线**：Electron 主进程直连 `RpcClient`；React 渲染层做界面；内置审批扩展补齐图形化确认能力。
- **对标可达成度**：Hermes/Codex 的键盘优先、单流对话、命令面板、会话管理等模式可完整复刻，并叠加 GUI 特有的 diff 卡片、会话树可视化等增强。
