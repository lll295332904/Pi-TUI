# PiDesk 产品化测试方案

> 用途：后续 agent 每完成一轮开发后，必须给出并执行/请求执行明确测试。本文定义 PiDesk 从代码检查到干净机安装验收的测试层级。
>
> 配套文档：`docs/06-agent产品开发执行文档.md`

## 1. 测试分层

PiDesk 测试分为 5 层：

1. 静态构建检查。
2. Pi runtime 资源检查。
3. 本机 release 冒烟测试。
4. 功能回归测试。
5. 干净机安装验收。

不同改动必须选择对应测试层级。

## 2. 每次代码改动必跑

### 2.1 前端构建

```bash
npm run build
```

通过标准：

- `tsc` 无错误。
- `vite build` 成功输出 dist。

### 2.2 Rust 检查

```bash
cd src-tauri
cargo check
```

通过标准：

- 无编译错误。
- 新增 warning 需要解释或修掉。

## 3. 涉及 release / Pi runtime / 打包 必跑

### 3.1 重新打包 Pi runtime

```bat
scripts\bundle-pi.bat
```

检查资源：

```bash
test -f src-tauri/pi-bundle/node.exe
test -f src-tauri/pi-bundle/package.json
test -f src-tauri/pi-bundle/dist/rpc-entry.js
test -f src-tauri/pi-bundle/dist/index.js
test -d src-tauri/pi-bundle/node_modules
```

### 3.2 构建 release

```bash
npm run tauri -- build
```

通过标准：

- 生成 NSIS setup.exe。
- 生成 MSI。
- release 目录中包含完整 `pi-bundle`。

检查命令：

```bash
find src-tauri/target/release \
  -path '*pi-bundle/package.json' -o \
  -path '*pi-bundle/dist/rpc-entry.js' -o \
  -path '*pi-bundle/dist/index.js' -o \
  -path '*pi-bundle/node_modules/openai/package.json' -o \
  -path '*pi-bundle/node.exe'
```

必须看到：

```text
src-tauri/target/release/pi-bundle/dist/index.js
src-tauri/target/release/pi-bundle/dist/rpc-entry.js
src-tauri/target/release/pi-bundle/node.exe
src-tauri/target/release/pi-bundle/node_modules/openai/package.json
src-tauri/target/release/pi-bundle/package.json
```

### 3.3 Bundled Pi RPC 入口探测

在 Git Bash 中执行：

```bash
WIN_BUNDLE=$(cygpath -w "$PWD/src-tauri/pi-bundle")
PI_PACKAGE_DIR="$WIN_BUNDLE" ./src-tauri/pi-bundle/node.exe ./src-tauri/pi-bundle/dist/index.js --version

timeout 3s env PI_PACKAGE_DIR="$WIN_BUNDLE" ./src-tauri/pi-bundle/node.exe ./src-tauri/pi-bundle/dist/rpc-entry.js
```

通过标准：

- 不报 `Cannot find module`。
- 不报 `ENOENT ... theme/dark.json`。
- 不报 `dist/index.js` 缺失。
- RPC 入口在无 stdin 探测中正常退出或等待，不出现启动崩溃。

注意：

- `PI_PACKAGE_DIR` 必须使用 Windows 原生路径，不能直接用 `/c/Git/...`，否则 Windows Node 可能错误解析成 `C:\c\Git\...`。

## 4. 本机 UI 冒烟测试

适用场景：

- 改了 `App.tsx`。
- 改了 `pi_kernel.rs` / `pi_locator.rs`。
- 改了 session / prompt / bridge。
- 改了 Settings / Provider / Setup Wizard。

步骤：

1. 启动开发模式：

```bash
npm run tauri -- dev
```

2. 检查应用能打开。
3. 新建会话。
4. 输入：

```text
你好，回复一句话。
```

5. 验证：

- UI 不弹 cmd。
- 状态从 idle -> streaming/running -> idle。
- 有 assistant 回复。
- Console 面板能看到 pi:event。
- 如果失败，UI 有可见错误，而不是只卡 running。

## 5. 功能回归测试清单

### 5.1 会话生命周期

测试项：

- 新建会话。
- 发送 prompt。
- abort 正在运行任务。
- compact。
- 删除会话。
- 关闭应用再打开。
- 恢复历史会话。

通过标准：

- 状态不残留 running。
- 删除会话后 UI 和磁盘一致。
- 重启后历史仍可见。

### 5.2 Provider / 模型

测试项：

- 添加 Provider。
- 填 API Key。
- 拉取模型。
- 设置默认模型。
- 切换 thinking level。
- 删除模型。

通过标准：

- 有效配置可保存。
- 错误配置有清晰错误。
- 新会话使用默认模型。

### 5.3 工具调用

测试项：

- 只读工具：让 agent 读取项目文件。
- bash 工具：执行安全命令，例如 `pwd`。
- edit/write 工具：仅在测试沙盒文件中验证。
- 审批策略开启时，危险工具弹窗。

通过标准：

- 工具卡片显示开始、输出、结束。
- 拒绝审批后工具不执行。
- 允许后工具执行。

### 5.4 错误恢复

测试项：

- 启动后手动 kill Pi 子进程。
- 删除 `pi-bundle/package.json` 后启动。
- 填错 API Key。
- 断网后发送 prompt。

通过标准：

- UI 显示错误和恢复入口。
- 可导出诊断信息。
- 不出现永久 running。

## 6. 干净机安装验收

这是判断“setup.exe 安装即用”的最终标准。需要 Windows Sandbox / VM / 一台未安装 Node/npm/Pi 的电脑。

### 6.1 环境准备

确认：

- 没有 Node。
- 没有 npm。
- 没有全局 pi。
- 没有已有 `~/.pi` 配置，或先重命名为备份。

### 6.2 安装测试

步骤：

1. 复制 `src-tauri/target/release/bundle/nsis/PiDesk_0.2.0_x64-setup.exe` 到干净机。
2. 双击安装。
3. 从开始菜单启动 PiDesk。
4. 观察是否弹出 cmd。
5. 等待首次启动界面。

通过标准：

- 应用能启动。
- 不弹 cmd。
- 不要求用户安装 Node/npm/Pi。
- 如果缺配置，进入 Setup Wizard，而不是空白主界面。

### 6.3 首次配置测试

步骤：

1. 选择 OpenAI-compatible Provider。
2. 填入 Base URL 和 API Key。
3. 点击测试连接。
4. 拉取模型列表。
5. 选择默认模型。
6. 选择默认工作目录。
7. 完成向导。

通过标准：

- 测试连接成功。
- 模型列表可选。
- 配置保存后进入主界面。
- 重启应用后配置仍存在。

### 6.4 第一条 prompt 测试

步骤：

1. 新建会话。
2. 输入：

```text
你好，回复一句话。
```

3. 等待回复。

通过标准：

- 有流式或完整 assistant 回复。
- 状态最终回到 idle。
- Console 无启动失败错误。

### 6.5 历史恢复测试

步骤：

1. 关闭应用。
2. 重新打开。
3. 检查历史会话是否存在。
4. 打开历史会话并继续发一条消息。

通过标准：

- 历史会话可见。
- 内容可恢复。
- 可以继续对话。

### 6.6 异常配置测试

步骤：

1. 修改 API Key 为错误值。
2. 发送 prompt。

通过标准：

- 显示认证失败或 provider 错误。
- 不永久 running。
- 提供返回 Settings / 修改配置入口。

## 7. 性能测试

### 7.1 长输出

Prompt：

```text
请输出 200 行编号文本，每行一句话。
```

检查：

- UI 不明显卡死。
- 滚动正常。
- 状态能回 idle。

### 7.2 多工具输出

Prompt：

```text
请列出当前项目的前 20 个源文件，并读取 package.json 总结技术栈。
```

检查：

- 多个工具卡片渲染正常。
- Console 不无限增长到明显卡顿。

### 7.3 多会话

步骤：

1. 连续创建 3 个会话。
2. 每个会话发送一条 prompt。
3. 切换会话。

检查：

- 每个会话状态独立。
- 不串消息。
- 关闭应用时进程能清理。

## 8. 测试汇报模板

后续 agent 完成工作后必须按此模板给出测试方案和结果：

```text
测试范围：<本次改动模块>

已执行：
- npm run build: 通过/失败
- cargo check: 通过/失败
- npm run tauri -- build: 通过/失败/不适用
- 本机 UI 冒烟: 通过/失败/不适用

关键结果：
- <列出真实输出或关键现象>

需要用户测试：
1. <步骤>
2. <步骤>

通过标准：
- <明确标准>

未覆盖风险：
- <没有则写“无”>
```

## 9. 不允许的测试汇报

不允许只写：

- “应该可以”。
- “理论上没问题”。
- “未测试但改动很小”。
- “npm run test 失败因为没有测试”。

必须给出真实执行过的命令，或者明确说明需要用户在干净机执行的步骤。
